 1. WHAT AK-DATA IS  ak-data info overview
    ────────────────────────────────────────────────────────────────────────
    AK-DATA (Arkadia Data Format) is a text format for JSON data that is
    read by language models. A <header> names every field once, with its
    type; the data that follows lists only values, by position. It carries
    exactly the same information as JSON — decoding always returns the
    original — in roughly half the tokens.

      # compact form (one line, for prompts)
      <users:<[id:number,name:string,active:bool]>>([(1,"Ada",true),(2,"Alan",false)])
      → {"users":[{"id":1,"name":"Ada","active":true},{"id":2,"name":"Alan","active":false}]}

      # readable form: the same text with whitespace (insignificant)
      <users:<[id:number, name:string, active:bool]>>
      ([
        (1, "Ada", true),
        (2, "Alan", false)
      ])
      → {"users":[{"id":1,"name":"Ada","active":true},{"id":2,"name":"Alan","active":false}]}

    Read it like this: <users:…> says the root is a record with one field
    users; <[…]> says that field is a list whose every element is a record
    (id, name, active). In the data, ( ) is a record and [ ] a list. Only
    the header has names; the data is positional.

    Design rules
    • Lossless: every JSON value has exactly one meaning in AK-DATA and
      decodes back to it (key order kept, 199.0 stays a float).
    • Schema first: structure is declared once, before the data, so a reader
      (or a model) knows the shape before the values.
    • Positional data: repeated keys disappear; nested records and lists stay
      positional at every level.
    • Irregular data is allowed: a value that does not fit its header carries
      its own type or keys (<string> "12", <any> {…}).
    • Metadata is not data: comments, $attr=… and #tags help the reader and
      are ignored when decoding.

 2. DOCUMENT STRUCTURE  ak-data info document
    ────────────────────────────────────────────────────────────────────────
    A document is: optional metadata, optional named type declarations, an
    optional root header, then exactly one value.

      document  =  meta*  ( '@' Name header  meta* )*  header?  meta*  value  meta*

      # all four parts
      /* optional comment */
      @Point<x:number,y:number>
      <start:@Point,end:@Point>
      ((0,0),(3,4))
      → {"start":{"x":0,"y":0},"end":{"x":3,"y":4}}

    • The value can be anything: a record ( ) or { }, a list [ ], or a
      primitive. Without a header it is read as plain data.
    • Whitespace and line breaks are allowed between any two tokens and mean
      nothing (except inside strings).
    • Compact form: one line, no optional spaces, newlines in strings written
      as \n — the form for prompts. Readable form: the same tokens with spaces
      and indentation.
    • Text is UTF-8; any character is allowed inside strings. Usual file
      extensions: .akd, .ak-data. In chat, put it in a
      `akd fence or between  <data>…</data> .
    • ANSI colour codes (from a terminal) are stripped before decoding, so
      coloured output can be pasted back.

 3. PRIMITIVE VALUES  ak-data info values
    ────────────────────────────────────────────────────────────────────────

      "Ada"                  string — always in double quotes
      "a \"b\" \\ \n"        escapes: \" \\ \n \t \r; any other \x is x
      42  -7  0              number (integer)
      199.0  3.14  -2.5e-3   number (float; 199.0 stays 199.0)
      true  false            bool
      null                   null — fits every type

      # a record without a header: fields are named _0, _1 …
      ("Zoë","line 1\nline 2",-0.5,1e3,true,null)
      → {"_0":"Zoë","_1":"line 1\nline 2","_2":-0.5,"_3":1000.0,"_4":true,"_5":null}

    • Numbers are written as in JSON: no +, no thousands separators, no
      units, no NaN / Infinity. 1e3 is a float.
    • Lenient reading: an unquoted word in data is read as a string ((Ada) →
      "Ada"). Writers must still quote every string — true, false, null and
      numbers are the only bare values.

 4. HEADERS AND TYPES  ak-data info header
    ────────────────────────────────────────────────────────────────────────
    A header <…> declares the shape of the value after it: a record with
    fields in order, a list, or a primitive type. Field order is the
    position of the value in the record.

      <a:type,b:type>               record with fields a, b (positions 0, 1)
      <[a:type,b:type]>             list whose every element is that record
      <[string]>                    list of strings (any element type)
      <number>                      a single primitive
      f:<x:number,y:number>         field holding a nested record
      f:<[sku:string,qty:number]>   field holding a list of records
      f:[string]                    field holding a list of strings
      f:[[number]]                  list of lists (matrix)
      f:[<a:number>]                same as f:<[a:number]>
      f:@User                       field of a named type (see: named)
      f                             field without a type = any

    Types

      type     values
      string   "…"
      number   42, 3.5, -1e-3   (int and float are accepted aliases)
      bool     true, false
      null     null
      any      anything; the value decides
      binary   a string (e.g. base64); kept as is

    Field names
    A name is an identifier — letters, digits and _, not starting with a
    digit. Anything else goes in backticks:
    <`user id`:number,`e-mail`:string,`2fa`:bool>. In headers only
    backticks are allowed for names (not double quotes).

      <`user id`:number,`e-mail`:string>(17,"ada@example.com")
      → {"user id":17,"e-mail":"ada@example.com"}

      # header without types (--no-types): every field is any
      <id,name>(1,"Ada")
      → {"id":1,"name":"Ada"}

 5. RECORDS: POSITIONAL ( ) AND NAMED { }  ak-data info records
    ────────────────────────────────────────────────────────────────────────

    Positional record ( )
    Values follow the header order: the n-th value belongs to the n-th
    field, at every nesting level.

      # nested record and nested list stay positional
      <id:string,customer:<id:number,name:string>,items:<[sku:string,qty:number]>,total:number>
      ("A1",(7,"Ada"),[("KB-01",2),("MS-02",1)],178.0)
      → {"id":"A1","customer":{"id":7,"name":"Ada"},"items":[{"sku":"KB-01","qty":2},{"sku":"MS-02","qty":1}],"total":178.0}

      # fewer values: the missing fields are absent (not null)
      <a:number,b:number,c:number>(1,2)
      → {"a":1,"b":2}

      # more values: extra fields are named _1, _2 …
      <a:number>(1,2,3)
      → {"a":1,"_1":2,"_2":3}

      # no header: fields are named _0, _1 …
      (1,"x")
      → {"_0":1,"_1":"x"}

    Named record { }
    Keys written next to the values — for a record without a header or one
    that does not fit it. Keys are identifiers, backticks or double-quoted
    strings.

      {id:1,name:"Ada",`e-mail`:"ada@example.com","":0}
      → {"id":1,"name":"Ada","e-mail":"ada@example.com","":0}

      # inside a list with a header, a named record keeps its own keys
      <[name:string,tools:[string]]>[("planner",["search"]),<any> {name:"writer",temperature:0.4}]
      → [{"name":"planner","tools":["search"]},{"name":"writer","temperature":0.4}]

      # a named record may also follow a header (keys matched by name)
      <a:number,b:string>{b:"x",a:1}
      → {"b":"x","a":1}

 6. LISTS  ak-data info lists
    ────────────────────────────────────────────────────────────────────────

      # list of values
      [1,2,3]
      → [1,2,3]

      # with an element type
      <[number]>[1,2,3]
      → [1,2,3]

      # list field
      <tags:[string]>(["a","b"])
      → {"tags":["a","b"]}

      # empty list
      <tags:[string]>([])
      → {"tags":[]}

      # list of records sharing one header
      <[id:number,tags:[string]]>[(1,["a"]),(2,[])]
      → [{"id":1,"tags":["a"]},{"id":2,"tags":[]}]

      # list of lists
      <km:[[number]]>([[0,293],[293,0]])
      → {"km":[[0,293],[293,0]]}

      # mixed list: values of another type carry it
      <[number]>[1,<string> "two",null]
      → [1,"two",null]

      # optional last field: the second record has only id and name
      <[id:number,name:string,email:string]>[(1,"Ada","a@x.io"),(2,"Alan")]
      → [{"id":1,"name":"Ada","email":"a@x.io"},{"id":2,"name":"Alan"}]

      # $size=N: the number of items, for the reader (enc --sizes)
      <rows:<[d:string,v:number]>>([//$size=3// ("mon",4),("tue",7),("wed",2)])
      → {"rows":[{"d":"mon","v":4},{"d":"tue","v":7},{"d":"wed","v":2}]}

 7. TYPE AND SHAPE OVERRIDES  ak-data info overrides
    ────────────────────────────────────────────────────────────────────────

    A value whose type or shape is different from its header says so itself,
    so mixed and irregular data stays lossless.

      <string> "12"   type override: a string where the header says number
      <number> 3001   a number in a string column
      <any> {k:v}     a record with its own keys (shape differs)
      <any> [ … ]     a list where the header says something else
      <null> null     an absent nested record (null alone also works)
      <a:number>(1)   any value may carry its own inline header

      # a number SKU and a text stock in typed columns
      <[sku:string,price:number,stock:number]>[("KB-01",89.0,14),(<number> 3001,null,120),("HD-10",129.9,<string> "on order")]
      → [{"sku":"KB-01","price":89.0,"stock":14},{"sku":3001,"price":null,"stock":120},{"sku":"HD-10","price":129.9,"stock":"on order"}]

      # missing nested record
      <[id:number,addr:<city:string,zip:string>]>[(1,("Kraków","30-001")),(2,<null> null)]
      → [{"id":1,"addr":{"city":"Kraków","zip":"30-001"}},{"id":2,"addr":null}]

 8. NAMED TYPES @TYPE  ak-data info named
    ────────────────────────────────────────────────────────────────────────

    @Name<…> declares a header once under a name; @Name uses it in other
    headers; @Name(…) gives a value that type. Declarations come before the
    root value; a later declaration with the same name replaces the earlier
    one. Encoders write inline headers — named types are for hand-written
    data and long schemas.

      @User<id:number,name:string>
      <team:string,lead:@User,members:[@User]>
      ("core",(1,"Ada"),[(2,"Alan"),(3,"Grace")])
      → {"team":"core","lead":{"id":1,"name":"Ada"},"members":[{"id":2,"name":"Alan"},{"id":3,"name":"Grace"}]}

      # a root value of a named type
      @Point<x:number,y:number>
      @Point(3,4)
      → {"x":3,"y":4}

 9. COMMENTS, ATTRIBUTES, TAGS  ak-data info metadata
    ────────────────────────────────────────────────────────────────────────

    Notes for the reader. They may appear between any tokens (before or
    after a value, between fields) and are skipped when decoding: the JSON
    is the same with or without them.

      /* text */                  comment (may nest: /* a /* b */ c */)
      $key=value                  attribute: $unit="EUR" $max=5, or any value: $range=[1,5]
      $required                   flag on a header field: the field must be present
      #tag                        tag: #draft #pk
      // $source="db" #v2 //      meta block: a group of attributes and tags
      [//$size=90// …]            number of items of a list (enc --sizes): models need not count
      // $changes=<[…]>[(…)] //   history of the document (ak-data merge / apply / history)

      // $source="crm" #snapshot //
      <customers:<[id:number /* pk */,plan:string $values="free|pro",mrr:number]>>
      ([(1,"pro",99) #trial,(2,"free",0)])
      → {"customers":[{"id":1,"plan":"pro","mrr":99},{"id":2,"plan":"free","mrr":0}]}

    An attribute value can be structured — a list or a record with its own
    header. It is still metadata: the history $changes written by
    ak-data merge and ak-data apply sits after the data and never changes
    what the document decodes to.

      # data with its history
      <n:number>(3)
      // $changes=<[id:string,title:string,changes:<[op:string,path:string,old:number,new:number]>]>[("9f3c2a1b7e","Bump",[("change","n",2,3)])] //
      → {"n":3}

10. WHAT ENCODERS WRITE (CANONICAL FORM)  ak-data info encoder
    ────────────────────────────────────────────────────────────────────────

    All encoders (Python, npm, Rust) write the same text for the same JSON.
    Knowing the rules helps to read real output:
    • Object → record with a header <…> and positional values ( ). Only an
      object with a key a header cannot spell (the empty key "", a name
      containing a backtick) is written as a named record { }.
    • List of objects with the same keys → <[…]> header taken from the first
      element, one ( ) per element. Key order in the header follows the first
      element; later elements are matched by name (the most common set of keys
      wins).
    • Records with optional fields → one header with every field, the most
      frequent first; a record that has only the first k fields is written
      with k values ((1,"Ada") under <[id,name,email]>). Used when it lets
      more records be positional than the most common exact layout.
    • An element that fits neither (other or extra keys) → <any> {key:value}
      in the list.
    • --sizes[=n] (Python dumps(sizes=n), npm dumps(data, {sizes: n})) adds
      //$size=N// to every list of n+ items.
    • A value of another type than its column → <type> value; null fits every
      type and needs no override.
    • Empty list → []; its element type comes from other records or is any.
    • Numbers: integers as integers, floats keep a fraction (199.0), very
      small/large floats in plain or exponent form as JSON.
    • Compact form escapes newlines in strings (\n); the readable form (
      ak-data read without -c) adds spaces and line breaks.
    • --no-types writes names only (<id,name>), --no-schema leaves out the
      header.

      # what the encoder writes for irregular input
      <a:number,b:[number],n:<[a:number,t:string]>>(1,[1,2,<string> "x"],[(1,"x"),(<string> "2","y"),(3,<any> {z:1})])
      → {"a":1,"b":[1,2,"x"],"n":[{"a":1,"t":"x"},{"a":"2","t":"y"},{"a":3,"t":{"z":1}}]}

11. JSON ↔ AK-DATA MAPPING  ak-data info json
    ────────────────────────────────────────────────────────────────────────

      JSON                   AK-DATA
      {"a": 1, "b": "x"}     <a:number,b:string>(1,"x")
      [{"a": 1}, {"a": 2}]   <[a:number]>[(1),(2)]
      [1, 2, 3]              <[number]>[1,2,3]
      {"t": ["x", "y"]}      <t:[string]>(["x","y"])
      {"o": {"k": true}}     <o:<k:bool>>((true))
      {"user id": 5}         <`user id`:number>(5)
      {"a": null}            <a:null>(null)
      [{"a": 1}, {"b": 2}]   <[any]>[{a:1},{b:2}]
      "text"                 <string>"text"
      {}                     {}
      []                     <[any]>[]

    Every row decodes to the JSON on its left; ak-data read file.json and
    ak-data read file.akd -t json convert both ways.

12. GRAMMAR (EBNF)  ak-data info grammar
    ────────────────────────────────────────────────────────────────────────

      document   = meta* { "@" name header meta* } [ header meta* ] value meta*
      
      header     = "<" [ fields | "[" element "]" | type ] ">"
      fields     = field { "," field }
      field      = meta* name [ ":" type ] meta*
      element    = fields | type | header
      type       = prim | "any" | "[" type "]" | header | "@" name [ header ]
      prim       = "string" | "number" | "int" | "float" | "bool" | "null" | "binary"
      
      value      = meta* ( typed | record | named | list | prim_value )
      typed      = header value                       (* override / inline header *)
                 | "@" name value
      record     = "(" [ value { "," value } ] ")"    (* positional *)
      named      = "{" [ key ":" value { "," key ":" value } ] "}"
      key        = name | string
      list       = "[" [ value { "," value } ] "]"
      prim_value = string | number | "true" | "false" | "null" | word
      
      name       = ident | "`" { any char except "`" } "`"
      ident      = ( letter | "_" ) { letter | digit | "_" }
      string     = '"' { char | "\" escape } '"'      (* \n \t \r, else literal *)
      number     = [ "-" ] digits [ "." digits ] [ ( "e" | "E" ) [ "+" | "-" ] digits ]
      
      meta       = comment | block | attribute | tag
      comment    = "/*" { any | comment } "*/"
      block      = "//" { attribute | tag | name [ "=" prim_value ] | comment } "//"
      attribute  = "$" ident [ "=" value ]           (* metadata, also when structured *)
      tag        = "#" ident

    Whitespace is allowed between all tokens. Decoding is error-tolerant:
    problems are collected with their positions (ak-data read --strict
    fails on any of them) and the rest of the document is still read.

13. WRITING AK-DATA (FOR PEOPLE AND MODELS)  ak-data info writing
    ────────────────────────────────────────────────────────────────────────

    Steps
    • Declare the structure first: copy the header you were given exactly, or
      write one — a list of results is <result:<[field:type,…]>>, one object
      is <field:type,…>.
    • Then one record per item, values in header order: [(…),(…)] for a list.
    • Quote every string; null for a missing value; plain numbers (1234.5,
      not "1 234,5 zł").
    • Nested objects are nested records ( ); nested lists [ ]; both declared
      in the header.
    • Before sending: every record has as many values as its header has
      fields; brackets balance; no trailing commas needed.

    Common mistakes

      ✗ <result:[name:string,total:number]>([("Ada",3)])
      ✓ <result:<[name:string,total:number]>>([("Ada",3)])
        a list of records is <[…]> inside the field: result:<[…]>

      ✗ <[name:string,total:number]>[(Ada,3)]
      ✓ <[name:string,total:number]>[("Ada",3)]
        strings are quoted (bare words are tolerated when reading, never write them)

      ✗ <[name:string,total:number]>[("Ada","1 234 zł")]
      ✓ <[name:string,total:number]>[("Ada",1234)]
        numbers without units, spaces or separators

      ✗ <[id:number,name:string]>[(1),(2,"Alan")]
      ✓ <[id:number,name:string]>[(1,null),(2,"Alan")]
        keep positions: write null for an unknown value

      ✗ <[name:string,total:number]>[{name:"Ada",total:3}]
      ✓ <[name:string,total:number]>[("Ada",3)]
        with a header, write positional records — keys again waste the tokens the header saved

      ✗ <"user id":number>(5)
      ✓ <`user id`:number>(5)
        names with spaces or symbols use backticks

      ✗ Sure! Here it is: <a:number>(1)
      ✓ <a:number>(1)
        when asked for "AK-DATA only": no prose and no ``` code fences

    Asking a model for AK-DATA

      Answer in AK-DATA only (no prose, no code fences), with exactly this header
      and one record per item:
      <result:<[country:string,orders:number,revenue:number]>>

    Give the definition (FORMAT_DEFINITION in the libraries), the data, the
    question and the header to fill. ak-data prompt and
    ak-data example --prompt build such prompts.
